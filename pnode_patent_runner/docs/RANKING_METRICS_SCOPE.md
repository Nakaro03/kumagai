# Hits@K / MRR と本リポジトリの主表スコープ

## 結論（査読・執筆で先に宣言する）

本リポジトリの **`run_benchmark_comparison`** および **`future_link_auc_scores` 系の既定プロトコル**は、future-link を **二値分類**として **ROC-AUC・Average Precision・ECE**（サブサンプル正例＋制約付き負例）で報告する。

**Hits@K・MRR（ランキング指標）は現行の主表スコープに含めない。**理由は次のとおり。

1. **評価集合の操作化**: 正例は最大 1500 本のサブサンプル、負例は active ノード上の部分集合であり、**全候補ペア上のランキング**ではない。Hits@K / MRR の定義（候補集合・フィルタリング）を論文とコードで別途固定しないと、査読で反証不能な主張になりうる。  
2. **実装コストと公平性**: 手法横断で **同一候補集合・同一ブレイクタイ**のランキング評価を追加するには、別スクリプトと JSON スキーマ拡張が必要。未実装のまま本文に書くと再現性の穴になる。

## 論文での書き方

- **主表**: AUC / AP / ECE のみ（本リポの JSON キーと一致）。  
- **Hits@K / MRR**: 「今後の拡張」または「候補集合を `hist_edges` 等で固定した上での別実験」と **Appendix に限定**するか、**スコープ外**と明記する。

将来ランキング指標を載せる場合は、[TREND_PREDICTION_EXPERIMENT.md](TREND_PREDICTION_EXPERIMENT.md) の正例・負例・RNG の節に倣い、**候補ペアの生成規則を数式と CLI で固定**すること。
